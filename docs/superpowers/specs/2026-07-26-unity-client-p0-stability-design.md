# Unity 客户端 P0 稳定性优化设计

## 背景

2026-07-26 的 macOS Player 盲审复现了四个入口级缺陷：

1. 冷启动时导航已出现，但主内容区为空。
2. 所有 `ApiRoutes` 使用根相对路径，而 `ApiClient` 将根相对路径误判为绝对地址并在发请求前抛出异常。
3. 会话恢复和登录缺少通用异常兜底，异常被表现为空白页或永久“正在登录”。
4. 实际 Player 中密码明文显示，键盘焦点也不够清晰。

用户已批准按审计建议直接开始优化，并要求不再逐项询问。

## 本阶段目标

本阶段只解决 P0 入口稳定性，不重做 K12 内容和整套视觉体验。完成后必须满足：

- 应用启动后始终显示加载页、登录页或主页，绝不出现空白主区。
- 根相对 API 路由安全拼接到配置的服务端 origin，跨 origin 的绝对 URL 仍被拒绝。
- 会话恢复或登录发生未预期异常时，用户看到可理解、可重试的错误，不会永久停在加载状态。
- 密码字段在运行时被强制设为密码模式。
- 键盘焦点在输入框和按钮上清晰可见。
- EditMode、PlayMode、静态验证和 macOS Player 人工入口流程都有新鲜证据。

## 方案比较

### 方案 A：只修改路由字符串

把所有 `/api/...` 改为 `api/...`。改动最小，但动态路由和未来新增路由仍容易再次犯错，也没有解决启动和异步错误状态。

### 方案 B：修复 URL 边界并补入口状态机（采用）

让 `ApiClient` 明确接受相对与根相对路由，同时拒绝 HTTP(S) 绝对路由；启动时先渲染 Loading；会话恢复与登录统一落入可见错误状态；密码和焦点增加运行时保护。

这个方案修复根因，又保持现有服务端协议、ScreenRouter 和 UI Toolkit 架构不变。

### 方案 C：引入完整全局异步任务框架

一次性替换 Presentation 层所有 `async void` 和 fire-and-forget。覆盖更广，但超出入口修复范围，回归风险过高，应在 P0 稳定后单独实施。

## 组件设计

### API URL 边界

`ApiClient.BuildUrl` 将：

- 拒绝空路由。
- 拒绝带 `http://` 或 `https://` origin 的绝对地址。
- 接受 `api/...` 和 `/api/...`。
- 用配置 origin 和去掉前导斜杠后的路由拼接唯一请求 URL。

EditMode 测试通过真实 `UnityWebRequest.url` 验证最终行为，不断言私有实现。

### 启动状态

`ScreenRouter` 新增 `Loading` 页面。`WordQuestApp.BuildUi` 完成后立即显示 Loading，再开始会话恢复。

会话恢复的结果只有三种：

- 成功：进入主页。
- API 返回失败：进入登录页并展示连接提示。
- 抛出异常：记录异常并进入登录页，展示可恢复提示。

应用销毁导致的取消不再制造错误提示。

### 登录状态

`LoginScreen` 提供可等待的登录/注册操作，按钮事件只负责调用它。无论 API 返回失败还是抛出异常，按钮都会恢复；异常转换为“暂时无法连接学习服务，请稍后重试”。

密码字段在构造时防御性设置 `isPasswordField = true`，避免模板或构建缓存失配。

### 焦点反馈

沿用森林绿、羊皮纸和金色 token，不引入新视觉语言。输入框和所有按钮在 `:focus` 状态下使用更粗的金色边框，同时保留现有 hover 反馈。

## 测试策略

1. EditMode：根相对路由可生成正确 URL；绝对 HTTP(S) 路由被拒绝。
2. EditMode：LoginScreen 即使收到未配置的密码字段，也会强制遮罩。
3. EditMode：认证服务抛异常后，状态文本可读且按钮恢复。
4. PlayMode：Bootstrap 第一帧后主内容区非空，并显示 Loading 或 Login。
5. 全量运行静态验证、EditMode、PlayMode。
6. 重建 macOS Player，人工验证冷启动、密码遮罩、离线登录错误和键盘焦点。

## 非目标

- 本阶段不重做首页信息架构。
- 本阶段不转换 CET-4 内容为 K12 课程内容。
- 本阶段不替换全部 Presentation 异步调用。
- 本阶段不改变服务端 API。
